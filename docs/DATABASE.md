# PostgreSQL foundation

`database/schema.sql` is a proposed schema, not a migration system or implemented
persistence layer. The Day 1 API uses process-local dictionaries and never connects
to PostgreSQL. SQL has not been applied or integration-tested against a database.

| Entity | Purpose and relationships |
| --- | --- |
| merchants | Merchant identity placeholder; no login implementation |
| transactions | Merchant transaction, provider reference, exact amount, timestamp |
| evidence_documents | Merchant-owned metadata and private object storage key |
| evidence_links | Many-to-many links between transactions and evidence documents |
| analysis_runs | Transaction job state, nullable draft/failure code, approval flag |
| findings | Issue, severity, explanation, recommendation for an analysis run |
| finding_sources | Many-to-many provenance links between findings and documents |
| audit_events | Merchant event, optional actor/resource/request reference, metadata |

All internal primary keys are UUIDs, generated by future application code. No UUID
extension or server default is required. Fixtures intentionally use readable opaque
string IDs and are not database seed records. `NUMERIC(12,2)` stores monetary values
exactly; API amounts remain strings. Currency is constrained to three uppercase
letters. Timestamps use TIMESTAMPTZ; application code must update `updated_at` when
jobs change (there is no trigger).

Uniqueness on `(merchant_id, paypal_transaction_id)` prevents duplicate provider
transactions per merchant. Composite `(merchant_id, id)` keys and foreign keys
prevent cross-merchant relationship links when this schema is deployed. This is
referential integrity, not authorization. There is no row-level security or access
control in the mock API. Future authenticated queries must derive merchant identity
from trusted credentials and filter every read/write by it; RLS and scoped object
storage authorization should be considered and tested before production.

Indexes support merchant/date transaction queries, transaction/evidence links,
analysis history and state, finding/source lookups, and chronological audit queries.
Unique indexes also cover merchant/provider references and link deduplication.
All delete behavior defaults to PostgreSQL NO ACTION: no cascading evidence or audit
deletions. Retention and deletion policy remain to be designed.

Uploaded bytes belong in private object storage, never database blobs or public URLs.
Store keys, names, content types, byte size, and optional SHA-256 metadata here. No
upload path, bucket, signed URL generator, or storage service is implemented. Future
services must validate metadata and enforce ownership; a finding's document also
needs semantic validation against its run's transaction evidence (not guaranteed by
these foreign keys). `evidence_count` is intended to be derived from evidence_links,
not stored redundantly. Its current value of 2 is synthetic.

`audit_events.resource_id` is a nullable polymorphic reference, not a foreign key;
future application code must validate it. Audit metadata must exclude credentials
and private document content. Append-only audit protections are not yet implemented.
The approval flag is constrained to true for this stage; approval/submission needs
a separately designed workflow. Failure codes are reserved in SQL but not exposed
by the current Analysis contract. Schema deployment, migrations, transaction
boundaries, durable jobs, access controls, and database tests are future work.


## Integration update — 2026-10-22

The API now stores uploaded bytes in a private temporary directory and maintains
metadata, facts, jobs, and full validated pipeline results in process-local memory.
This is not PostgreSQL or durable object storage. No schema changes were needed.
Evidence counts are now derived from uploaded records; the illustrative fixture's
count of 2 is no longer used as the runtime count. Restart/reload discards metadata
and results; clean shutdown removes files. The persistence/security work above
remains outstanding. See INTEGRATION-VERIFICATION.md for the tested local workflow.

## Current application schema

Alembic creates the isolated `proofpay` schema without modifying historical public
tables: merchants, users, sessions, transactions, evidence_documents, analysis_runs,
findings, finding_sources, draft_responses, draft_revisions, audit_events and
idempotency_keys. `database/migrations/schema_v1.py` is the frozen migration snapshot;
`backend/db/models.py` is runtime metadata. Destructive downgrade is disabled.

Scoped external/API IDs are unique; money is Numeric(12,2). Composite merchant/
resource foreign keys enforce child ownership. Each document's direct transaction
FK is its persisted association; source rows reference both finding and document.
JSONB preserves public contracts and provenance. Binary files stay outside SQL.
Snapshot updates are transactional; audit events are append-only in the application.

A per-merchant cache has a single-process advisory lease. SQL is the durable source
reloaded on restart. This small implementation saves merchant snapshots and filters/
paginates the cache; large datasets need incremental writes and SQL pagination.
